# Fresh-consent recovery after undiscovered authorization expiry

`ConsentService.Supersede` can acknowledge a fresh, provider-verified replacement for an expired authorization that never completed discovery. The previous connection **stays Revoked**. The operation neither unseals old credentials nor calls a provider, restores authority, repeats revocation, or certifies backup deletion.

The narrow recovery case requires confirmed primary revocation/erasure and the unclaimed-expiry event, no retained credentials/inventory/scopes/lease/subject or verification timestamp, and no historical ready/discovery-progress event. The old browser return must have been redeemed before the session expired. Previously verified or partially discovered revoked accounts are deliberately excluded: their erased identity cannot safely be inferred from an arbitrary replacement.

The replacement must belong to the same deployment, installation, profile/public revision and reviewed package. Its consent must be redeemed, use the same actor, declaration, policy and exact permission sets, and have begun after confirmed old revocation. It must be Ready with a current, non-future verification timestamp and a verified subject, protected credentials/inventory and no active lease. The existing consent, expiry and discovery checks remain in force. No business or agent grant is created.

The existing signed supersede route returns the old connection's actual `Revoked` snapshot. A `connection.revoked-replacement-linked` event binds that acknowledgment to exactly one replacement in the same serializable transaction as both revision fences. It is an accounting receipt, not another primary-erasure receipt. Ordinary verified supersession retains `Superseded` status and now also binds its receipt to the replacement. A duplicate request for the same pair returns its existing receipt without another write, even after a later replacement disconnect; another candidate is rejected. Legacy supersession events without a bound target fail closed rather than guessing.

SQLite's immediate serializable transaction prevents a replacement disconnect or authority update from committing between validation and receipt persistence. A failed save rolls back both revision changes and the event. No new schema or protocol record is introduced: the existing event target column and Protocol 0.5.0 connection snapshot suffice. The protocol package is unchanged and must not be republished for this fix.

Deploy the reviewed service change before enabling the corresponding Core recovery flow. Deployment and live consent require separate approval. Regression tests use synthetic accounts/providers and SQLite only; they do not demonstrate provider acceptance or historical erasure of backups.
